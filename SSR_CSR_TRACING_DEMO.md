# 🔍 Testing the SSR / CSR Tracing Demo

This walks through verifying three reference implementations in `apps/ibe-app`:

- **§1–6: the `orders` demo** — `traceparent`-based trace correlation
  across a single SSR or CSR request
- **§6a: the external-system boundary** — `external_correlation_id`, used
  specifically for the flight flow's simulated PSS/POP call
- **§7: the `flight/*` demo** — `journey_id` correlation across an 8-page
  flow (search → ... → completion), where each page is its own trace

See `OTEL_COMPLETE_IMPLEMENTATION_GUIDE.md` for how the base OTEL setup
works, and `ARCHITECTURE.md` for the design reasoning behind all three.

---

## What You're Verifying

Two different paths that both end up at the same API route, backend, and
logging/tracing pipeline:

```
SSR:  page (server component) ────────────────────► /api/orders ─► server service ─► sdk ─► backend
CSR:  Redux dispatch ─► client service (browser) ──► /api/orders ─► server service ─► sdk ─► backend
```

What should hold true in both cases:
- Both callers send a `traceparent` header, generated client-side with `generateTraceparent()` — not a custom `x-correlation-id` header
- The `x-trace-id` the response returns is **exactly** the trace-id from that `traceparent` — the browser/SSR page chose it, the server didn't invent a new one
- Server-side logs for that request show the trace_id
- Jaeger shows the API route span, and — since the SDK's outbound call is auto-instrumented — a nested `fetch GET https://jsonplaceholder...` child span, all under the same trace ID
- A failing request still returns the trace ID, so it's reportable

## Setup

```bash
docker-compose up -d          # jaeger + otel-collector
pnpm --filter ibe-app dev     # http://localhost:3000
```

## 1. Verify the API Route Directly

This isolates the "api route → server service → sdk" chain from either caller.

```bash
curl -i http://localhost:3000/api/orders
```

**Check for:**
- `x-trace-id` header — a 32-char hex OTEL trace ID, generated by the server since nothing sent a `traceparent`
- Body: `{"success":true,"orders":[...],"traceId":"..."}` — matches the header

Now send a hand-crafted `traceparent` and confirm the server adopts its exact trace-id instead of generating its own:

```bash
curl -i http://localhost:3000/api/orders \
  -H "traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
```
`x-trace-id: 4bf92f3577b34da6a3ce929d0e0e4736` should come back **exactly** as sent — not a new, server-generated value. This is the core mechanism the whole `orders` demo relies on: `@vercel/otel` extracts `traceparent` automatically, before the route handler even runs.

---

## 2. Verify the SSR Path

```bash
curl -s http://localhost:3000/orders-ssr | grep -o 'traceId.\{0,60\}'
```

Or just open [http://localhost:3000/orders-ssr](http://localhost:3000/orders-ssr) in a browser and view source / check the rendered `traceId` value on the page.

**What's actually happening:** the page is a server component. It generates a `traceparent` with `generateTraceparent()` *before* fetching, then calls its own `/api/orders` over a real HTTP request (server components don't get an implicit base URL for self-fetches). There is no client service in this path — check `app/orders-ssr/page.tsx` to see it generated right there.

**Confirm it's a fresh trace each load:** refresh the page a few times — the `traceId` shown should differ each time, since a new `traceparent` is generated per-render.

---

## 3. Verify the CSR Path

Open [http://localhost:3000/orders](http://localhost:3000/orders) in a browser with DevTools open (Network tab).

1. Click **Fetch Orders**
2. Find the request to `/api/orders` in the Network tab
3. **Request Headers** — confirm `traceparent` is present, formatted `00-<32 hex>-<16 hex>-01` (generated in `orders-client-service.ts`, in the browser, before the fetch)
4. **Response Headers** — confirm `x-trace-id` matches the trace-id portion of the `traceparent` you just sent
5. On the page itself, the rendered `traceId` under the order list should match what you saw in the Network tab

**What's actually happening:** clicking the button dispatches a Redux thunk (`fetchOrders`). The thunk calls the client service, which generates the `traceparent` and does the fetch — Redux's `dispatch()` itself is synchronous; the actual network call and header generation happen inside the thunk body.

## 4. Confirm Trace Correlation in Jaeger

1. Take a `traceId` from any of the above (response header, or the page's rendered value)
2. Open [http://localhost:16686](http://localhost:16686)
3. Paste the trace ID directly into the search box (or select service `ibe-app` → Find Traces → pick the `/api/orders` trace)
4. You should see spans nested like:
   ```
   GET \api\orders\route                                    (root span for this request)
   └─ executing api route (app) \api\orders\route
      └─ fetch GET https://jsonplaceholder.typicode.com/...  ← the SDK's outbound call,
                                                                 auto-instrumented, same trace ID
   ```
5. Expand the API route span → **Logs** section should show `log.info` events (`"GET /api/orders called"`, `"GET /api/orders succeeded"`).

If the SDK's `fetch` span is missing, the auto-instrumentation isn't active — check that `instrumentation.ts` → `register()` ran (it logs nothing by itself, but the app should show `resolve page components` spans for every route in the collector logs if it's working at all).

---

## 5. Confirm the Trace ID Shows Up in Terminal Logs

While the dev server is running, trigger either path (step 1–3) and watch the terminal. You should see lines like:

```
[INFO] 2026-09-05T10:41:07.123Z api/orders - GET /api/orders called (trace=52bcc4d6...)
[INFO] 2026-09-05T10:41:07.145Z server/orders-service - Fetching orders (trace=52bcc4d6...)
[INFO] 2026-09-05T10:41:07.170Z sdk/backend-client - Calling backend (trace=52bcc4d6...)
[INFO] 2026-09-05T10:41:08.740Z sdk/backend-client - Backend call succeeded (trace=52bcc4d6...)
```

Every layer — API route, server service, sdk — logs with the **same**
`trace` value, even though none of them explicitly passed it to the next
one. That's OTEL's own context propagation doing its job (not
`AsyncLocalStorage` we wrote ourselves) — `getTraceContext()` returns the
right value anywhere downstream in the same async call chain.

## 6. Verify a Failure Still Carries the Trace ID

Temporarily break the backend call to see the failure path — e.g. edit `packages/sdk/src/index.ts` and change `BACKEND_BASE_URL` to something that will fail (`https://invalid.example.test`), or stop your network temporarily.

**API route directly:**
```bash
curl -i http://localhost:3000/api/orders
```
Expect `502` with a body like `{"success":false,"traceId":"...","error":"..."}` — the trace ID is still present on failure.

**CSR page:** click **Fetch Orders** — the page should show the red "Request failed" block with `traceId` still rendered. This confirms `ordersSlice.ts`'s `rejectWithValue` path is carrying the trace ID into Redux error state rather than losing it in a thrown error.

**In Jaeger:** the API route span should now show as **failed/red**, not a normal "OK" span — this is `span.recordException()` + `span.setStatus(ERROR)` firing because `logger.error()` was called with the caught error as its third argument.

Remember to revert `BACKEND_BASE_URL` afterward.

## 6a. Verify the External-System Boundary (`external_correlation_id`)

This is a separate mechanism from everything above — used specifically for
the flight flow's payment step, which simulates a call to an external
PSS/POP system that doesn't run OTEL. See `ARCHITECTURE.md` §4a.

```bash
rm -f /tmp/fc.txt
curl -s -c /tmp/fc.txt http://localhost:3000/flight/search -o /dev/null
for step in results seats passengers extras review payment; do
  curl -s -b /tmp/fc.txt -c /tmp/fc.txt http://localhost:3000/flight/$step -o /tmp/$step.html
done
grep -o 'externalCorrelationId[^<]*<code>[^<]*' /tmp/payment.html
```

**Confirm:**
- The `payment` page shows an `externalCorrelationId` value
- None of the other steps' saved HTML (`/tmp/seats.html`, `/tmp/review.html`, etc.) contain that pattern at all — it's scoped narrowly to the one external call, not the whole flow

**In the terminal logs**, confirm all three IDs coexist on the payment step only:
```
[INFO] ... server/flight-journey-service - Calling external PSS/POP for payment confirmation (journey=..., external=..., trace=...)
[INFO] ... sdk/backend-client - Calling external system (journey=..., external=..., trace=...)
```
and confirm `external=` is **absent** from the log lines for any other step (`results`, `seats`, etc.) — `runWithExternalCorrelationId()` only wraps that one call.

**In Jaeger**, the payment step's trace should show two separate outbound
`fetch` spans — one to `BACKEND_BASE_URL` (our own backend, via
`callBackend()`, no special header) and one to `EXTERNAL_SYSTEM_BASE_URL`
(via `callExternalSystem()`, carrying `x-external-correlation-id`) — using
different demo paths (`/todos/7` vs `/posts/1`) specifically so they're
easy to tell apart in the trace waterfall.

Remember to revert `BACKEND_BASE_URL` afterward.

## 7. Verify the Multi-Page Journey (`journey_id`)

This is a different flow entirely — `apps/ibe-app/app/flight/*` (8 pages:
`search` → `results` → `seats` → `passengers` → `extras` → `review` →
`payment` → `completion`). Each page load is its own trace; `journey_id` is
what ties all 8 together. See `ARCHITECTURE.md` §4 for the full design.

### Walk the flow with a cookie jar

```bash
rm -f /tmp/flight-cookies.txt

# Step 1 - always issues a FRESH journey_id, even over a stale cookie
curl -s -c /tmp/flight-cookies.txt -D - http://localhost:3000/flight/search -o /tmp/search.html \
  | grep -i set-cookie

# Steps 2-8 - same journey_id should appear on every page
for step in results seats passengers extras review payment completion; do
  echo "=== $step ==="
  curl -s -b /tmp/flight-cookies.txt -c /tmp/flight-cookies.txt \
    http://localhost:3000/flight/$step -o /tmp/$step.html
  grep -o 'journeyId:.\{0,50\}' /tmp/$step.html | head -1
done
```

**Confirm:** the same `journeyId` value appears on all 8 pages.

### Verify the fallback path (deep link, no cookie)

```bash
curl -s -D - http://localhost:3000/flight/seats -o /tmp/deeplink.html | grep -i set-cookie
grep -o 'fallback journey_id[^<]*' /tmp/deeplink.html
```
Expect a **new** cookie to be issued and the page to show the
"⚠ fallback journey_id" warning — confirming a deep link mid-flow doesn't
silently pretend to be a normal journey start.

### Verify re-entry issues a fresh journey

```bash
echo "before:"; grep journey_id /tmp/flight-cookies.txt | awk '{print $7}'
curl -s -b /tmp/flight-cookies.txt -c /tmp/flight-cookies2.txt http://localhost:3000/flight/search -o /dev/null
echo "after:"; grep journey_id /tmp/flight-cookies2.txt | awk '{print $7}'
```
The two IDs should differ — hitting `/flight/search` again always starts a
new journey, even with a valid existing cookie.

### Verify the terminal logs

Same as the `orders` demo — but now every line carries `journey=` alongside
`trace=`, and it's the **same `journey=` value across many different
`trace=` values**:

```
[INFO] ... server/flight-journey-service - Journey step: search (journey=abc..., trace=111...)
[INFO] ... server/flight-journey-service - Journey step: results (journey=abc..., trace=222...)
[WARN] ... pages/flight-flow - journey_id missing on entry, generated fallback (journey=xyz..., trace=333...)
[INFO] ... pages/flight-flow - Journey completed (journey=abc..., trace=888...)
```

### Verify Jaeger's tag search returns all 8 traces

This is the actual point of the feature — a single query pulling up an
entire booking attempt from 8 separate traces:

```bash
JID="<paste a journeyId from any /flight/* page>"
curl -s -G "http://localhost:16686/api/traces" \
  --data-urlencode "service=ibe-app" \
  --data-urlencode "tags={\"journey_id\":\"$JID\"}" \
  --data-urlencode "limit=20" | node -e "
let raw='';process.stdin.on('data',c=>raw+=c).on('end',()=>{
const d=JSON.parse(raw);const traces=d.data||[];
console.log('traces returned:', traces.length);
for(const t of traces){const steps=new Set(),status=new Set();
for(const s of t.spans)for(const tag of (s.tags||[])){if(tag.key==='journey_step')steps.add(tag.value);if(tag.key==='journey_status')status.add(tag.value);}
console.log(' ', t.traceID.slice(0,16), '| step:', [...steps].join(',')||'-', '| status:', [...status].join(',')||'-');}
});"
```

Or in the Jaeger UI directly: **Find Traces** → service `ibe-app` → Tags
field → `journey_id=<id>` → **Find Traces**. Expect **8 results**, one per
step, with the completion trace additionally tagged `journey_status=completed`.

You can also confirm this the other way, in the Jaeger UI: open any single
`/flight/*` trace, expand its root span, and check the **Tags** section for
`journey_id` and `journey_step` — if `journey_id` only appears inside a
**Logs** event (not as a top-level tag), the tag search above won't find it;
it needs to be a real span tag, per `ARCHITECTURE.md` Decision 7.

| The 8 flow pages | `apps/ibe-app/app/flight/{search,results,seats,passengers,extras,review,payment,completion}/page.tsx` |

## Troubleshooting

**No `x-trace-id` header at all** — the request never reached an instrumented span. Confirm `instrumentation.ts` exists at the app root and exports `register` from `@yourorg/otel`.

**`x-trace-id` doesn't match the `traceparent` I sent** — confirm the header name is exactly `traceparent` (not `x-traceparent` or similar) and the format is `00-<32 hex>-<16 hex>-01`. A malformed value is silently ignored and the server generates its own trace-id instead.

**Journey pages (or any page after adding middleware.ts) throw `Cannot read properties of undefined (reading 'attributeCountLimit')`** — this is the Edge-runtime bug described in `ARCHITECTURE.md` §4: adding `middleware.ts` makes Next.js invoke `instrumentation.ts` on Edge too, and `@vercel/otel` isn't Edge-safe. Confirm `instrumentation.ts` gates the import behind `process.env.NEXT_RUNTIME === "nodejs"`.

**`journey_id` tag search in Jaeger returns 0 results** — confirm `tagJourneyStep`/`tagJourneyStatus` are actually being called (check the terminal logs show `journey=` on that request) and that they use `span.setAttribute()`, not just `span.addEvent()` — only real span tags are searchable this way.

**Same `journey_id` unexpectedly appears across unrelated bookings** — likely two tabs/windows sharing one browser profile hit `/flight/search` around the same time; this is the known cookie tab-collision tradeoff in `ARCHITECTURE.md` Decision 6, not a bug.

**`external_correlation_id` appears on every step, not just payment** — check `runWithExternalCorrelationId()` is only called inside the `if (step === "payment")` block in `flight-journey-service.ts`, not wrapping the whole `recordJourneyStep()` function.

**Terminal logs show `trace=...` but no `external=...` on the payment step** — the log call happened outside `runWithExternalCorrelationId()`'s callback, or `callExternalSystem()` wasn't actually invoked. Confirm `logger.info`/`callExternalSystem()` calls happen *inside* the `runWithExternalCorrelationId(id, async () => { ... })` block.

**Browser build fails or bloats after touching `orders-client-service.ts`** — confirm the import is `@yourorg/otel/src/trace-context`, never `@yourorg/otel` (the main entry eagerly imports `@vercel/otel`, which is Node-only and unsafe in a browser bundle).

**SDK's fetch span missing from Jaeger** — see step 4 above.
